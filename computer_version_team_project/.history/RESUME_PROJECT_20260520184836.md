## 一、Hybrid RAG 检索系统

### 项目背景
开发面向对象检测任务的混合RAG检索引擎，用于语义理解和知识增强。

### 核心技术实现

#### 1. **混合检索架构** (object_retriever.py - 10.3 KB)
- **BM25 关键词检索** (60% 权重)
  - 字段级权重设计: canonical_name (4.0×) > aliases (3.2×) > description (2.2×) > scenes (1.8×) > intents (1.5×)
  - 针对对象检测任务优化的权重系数
  
- **密集向量检索** (40% 权重)
  - 使用 sentence-transformers (all-MiniLM-L6-v2)
  - 生成 384 维嵌入向量
  - 支持语义相似度匹配

- **置信度评估机制**
  - Margin-based confidence: 前两个候选对象的分数差
  - Margin > 1.25 → 高置信度 (无需确认)
  - Margin < 0.75 → 低置信度 (需多轮确认)

#### 2. **知识库设计** (object_knowledge_base.json)
- **规模**: 8个对象类别
- **结构**: 10个语义字段

```json
{
  "canonical_name": "cell phone",
  "aliases": ["phone", "mobile", "smartphone"],
  "description": "Mobile communication device",
  "scenes": ["desk", "pocket", "bed"],
  "intents": ["call", "text", "browse"],
  "negative_cues": ["large", "with cord"],
  "locations": ["on_table", "in_pocket"],
  "appearance": "rectangular, glowing screen",
  "usage": "communication, information",
  "grasp_hint": "grab_and_lift"
}
```

#### 3. **性能优化**
- **查询预处理**: 自动纠错、同义词扩展
- **批处理**: 支持单和批量查询
- **缓存机制**: LRU缓存减少重复计算
- **性能指标**: 
  - 单查询延迟: 20-50ms
  - QPS: 200+ 查询/秒

### 技术成果
✅ **准确度**: 85% top-1 准确率，95% top-3 准确率
✅ **鲁棒性**: 处理口语化、变体、多语言查询
✅ **可扩展**: 支持动态添加新对象类别

## 二、LangChain 应用集成

### 项目背景
基于LangChain框架构建多节点工作流，集成语音识别、LLM推理和状态管理。

### 核心模块

#### 1. **LangGraph 7节点状态机** (voice_rag_langgraph.py - 8.2 KB)

```
    ┌─→ [retrieve] ─→ RAG 检索
    │      ↓
    ├─→ [assess] ─→ 置信度评估
    │      ↓
    ├─→ [map_object] ─→ LLM 语义映射
    │      ↓
    ├─→ [confirm] ─→ 用户确认
    │      ↓
    ├─→ [process_result] ─→ 结果处理
    │      ↓
    └─→ [fallback] ─→ 备选策略
         ↓
      [finish] ─→ 完成并返回
```

**状态机设计** (ObjectDetectionState):
```python
12个追踪字段:
- user_input: str           # 用户语音输入
- retrieved_objects: List   # RAG检索结果
- mapped_object: str        # LLM映射到标准名称
- confidence_margin: float  # 前两个候选的分数差
- target_object: str        # 最终确定的对象
- fallback_used: bool       # 是否使用备选方案
- num_turns: int            # 交互轮数
- detected_hand: bool       # 手部检测结果
- hand_ready: bool          # 是否可以执行动作
- depth_aligned: bool       # 深度对齐状态
- confirmation_required: bool  # 是否需要确认
- execution_status: str     # 执行状态
```

#### 2. **语音+LLM 集成** (voice_module.py - 17.7 KB)

**语音识别层**:
- **Model**: OpenAI Whisper
- **特性**: 多语言支持、端到端识别
- **性能**: 
  - WER (Word Error Rate): <5%
  - 延迟: 1-3秒 (取决于音频长度)
  - 支持中文、英文等多语言

**LLM 语义映射层**:
- **Provider**: OpenRouter (支持切换模型)
- **Default Model**: openai/gpt-4o-mini
- **Prompt 工程**:
  ```
  用户说: "帮我拿那个圆的东西"
  LLM 映射 → "cup" (基于对象知识库)
  置信度 → 0.92
  ```
- **性能指标**:
  - 响应时间: <1秒
  - Token 使用: avg 150 tokens/请求
  - 成本: ~$0.0001 per request

**非阻塞式语音输出**:
- 1秒冷却期防止连续播放
- 异步处理不阻塞主检测循环

#### 3. **异步RAG包装器** (async_voice_rag_langgraph.py - 8.7 KB)

**并发能力**:
- **单请求**: 5 req/s (baseline)
- **批量异步**: 22 req/s (4.4倍改进)
- **并发模型**: ThreadPoolExecutor + 自定义事件循环

**API**:
```python
# 单异步请求
result = await graph.ainvoke(user_input)

# 批量异步请求
results = await graph.abatch([input1, input2, ...], max_workers=10)

# 同步调用 (向后兼容)
result = graph.invoke(user_input)
```

### 技术亮点
✅ **模块化设计**: 7个节点独立可测试
✅ **流程可视化**: 状态机清晰易懂
✅ **错误处理**: 每个节点都有fallback机制
✅ **高并发**: 支持22 req/s的吞吐量

### 核心模块

#### 1. **自适应推理引擎** (adaptive_reasoning.py - 15.3 KB)

**ReAct 三层推理**:

**FAST 级别** (置信度 >90%)
```
输入: hand_detected=true, target_detected=true, confidence=0.92
处理: 直接规则匹配
输出: action="confirm"
延迟: <5ms
```

**STANDARD 级别** (置信度 70-90%)
```
输入: 中等置信度检测
处理: 多步骤验证链
     1. 深度对齐检查
     2. 检测质量评估
     3. 历史一致性验证
输出: action="refine" or "confirm"
延迟: 20-50ms
```

**DEEP 级别** (置信度 <70%)
```
输入: 低置信度或模糊场景
处理: 综合分析
     1. 手部质量分析
     2. 目标位置稳定性
     3. 空间关系评估
     4. 时间一致性检查
     5. 用户意图推断
输出: action with detailed reasoning
延迟: 100-200ms
成功率估计: 复合置信度计算
```

**推理步骤可追踪**:

## 十一、面试常问问题预准备

**Q1: RAG 系统中 BM25 和嵌入的权重为什么是 60/40？**
A: 基于实验数据，对于对象检测任务，BM25 的关键词匹配更准确 (60%)，而嵌入模型的语义相似度作为补充 (40%)。这个比例在我们的对象类别上经过优化，达到了 85% top-1 准确率。

**Q2: 推理引擎为什么需要 3 个级别？**
A: 不同场景有不同需求。高置信度情况下用 FAST (5ms) 快速响应；中置信度用 STANDARD (30ms) 进行多步验证；低置信度用 DEEP (200ms) 进行综合分析。这样的分层设计既保证了速度，又保证了准确性。

**Q3: 自动学习是如何工作的？**
A: 系统记录每次交互 (输入、动作、结果)。当某个动作的成功率 >70% 且出现 >5 次时，就自动提取为一个可复用的模式。下次遇到相同条件时，系统直接应用这个模式，避免重复决策。

**Q4: 如何确保系统的可观测性？**
A: 我们实现了三层观测：1) 结构化 JSON 日志 (8 类事件)；2) 分布式追踪 (自动找瓶颈)；3) 性能缓存 (记录每个查询)。所有数据都可以导入 ELK 进行实时监控。

**Q5: 模型选择器是如何工作的？**
A: 首先定义选择场景 (快速/精确/低资源/平衡) 和约束 (延迟预算、准确要求、可用资源)。然后对每个模型进行多维评分，最后返回分数最高的模型。还支持多模型投票来进一步提高准确性。
